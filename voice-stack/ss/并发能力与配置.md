# speech-to-speech 并发能力与配置

> 结论先行：**默认 6 路并发**。
>
> ⚠️ 本文数据已在 2026-09-12 延迟优化后重新采集。优化前（容器内自带
> whisper+kokoro 模型）6 路首包要 63 秒、占 12G 内存；**优化后 6 路首包 8.1 秒、占 517MB**。
> 具体改了什么见 `延迟优化说明.md`。

---

## 1. 并发模型

服务内部是**会话池**：池里有 N 个完全独立的 pipeline unit，一个 WS 连接占用一个。

```
WS 客户端 ─┬─→ unit 0   (VAD + 上游STT + 上游LLM + 上游TTS)
           ├─→ unit 1
           └─→ unit N-1 ...
```

- 状态流转 `idle → active → draining → idle`，断开后释放
- 池满时新连接收到 `1008 All session slots are in use`
- 源码刻意隔离每个 unit（防三方库 setup 阶段互相污染），所以 unit 之间不共享状态

**关键变化**：优化后 STT/TTS 走外部服务（9880），unit 里**不再加载任何模型**，
只保留 VAD（silero，几十 MB）。所以内存不再随路数线性增长 —— 内存不再是要考虑的问题。

## 2. 实测数据（优化后）

压测方式：`concurrent_test.py --n N`，N 路同时建会话、同时喂 3.48s 音频、同时等回复。

| 路数 | 成功率 | 首包延迟(中位) | 整轮耗时(中位) | 容器空闲内存 |
|---|---|---|---|---|
| 1 | 1/1 | **1.18s** | 1.3s | 517 MB |
| **6** | **6/6** | **8.1s** | **11.2s** | **517 MB** |
| 12 | 6/12 | 8.8s | 11.9s | — |

12 路里失败的 6 路全部是 `1008 池已满`，不是性能问题 —— 池大小就是 6。

### 为什么并发时首包从 1.2s 涨到 8.1s

因为**上游变成了串行瓶颈**，不再是本机模型：

- 6 路的 STT 请求都要过同一个 9880 `voice-service`（单实例）
- 6 路的 LLM 请求都要过同一个 `llama-server`（8080）
- 6 路的 TTS 请求也要过同一个 9880

注意这是「6 个人同时开口」的极端场景。真实通话中每路各说各话、请求天然错开，
不会同时爆发。

### 与优化前的对比

| 路数 | 首包中位 | 空闲内存 |
|---|---|---|
| 6（优化前） | 62.8s | 12 GB |
| **6（优化后）** | **8.1s** | **517 MB** |

## 3. 怎么调

```bash
# 改路数必须用 start 重建容器——restart 不会应用新环境变量
SS_NUM_PIPELINES=10 bash /opt/m/ss/ss-docker.sh start
```

确认：

```bash
bash /opt/m/ss/ss-docker.sh status      # 看「流水线池」的 size
wget -qO- http://127.0.0.1:8765/v1/pool # {"size":N,"in_use":0,...}
```

> ⚠️ 本机 `docker exec` 是坏的（见部署说明）。`restart` 等于 `start`（重建容器）。

### 选多少路

现在内存不是约束，**约束变成上游 9880 和 llama-server 的吞吐**：

| 场景 | 建议 |
|---|---|
| 单人/少量通话 | **2–4 路**（首包接近单路的 1.2s） |
| 多人同时接入（默认） | **6 路**（首包中位 8.1s） |
| 更高并发 | 可以往上加（内存够），但上游会先排队；真正的解法是给 STT/TTS/LLM 加实例 |

---

## 4. 还能怎么提

1. **上游扩容**：9880 和 llama-server 各跑 1 个实例，并发上去会排队。
   要真正提升并发，得让它们的实例数跟上。
2. **启用 GPU**：Jetson 的 GPU 现在是**空闲的**（llama-server 实际跑在 CPU 上，
   `nvidia-smi` 类节点读数为 0）。把 STT/TTS/LLM 挪到 GPU 能同时改善延迟与并发。
   容器侧需挂载 `/dev/nvidia*` 与宿主机 `libnvidia-ptxjitcompiler.so`，
   见部署说明「GPU」一节。
3. **降级 STT 模型**：如果改用回容器内本地模型，`SS_STT_MODEL=base` 比 `small` 快，
   中文精度会掉。
4. **换引擎**：9880 的 `/tts/vits` 支持 `engine=melo|fanchen`；
   当前用 `melo`（实测 0.42s，比 `fanchen` 快）。

## 5. 压测工具

`concurrent_test.py`（与本文件同目录，依赖 `websockets` + `numpy`）：

```bash
python concurrent_test.py --n 6                    # 6 路并发打一轮
python concurrent_test.py --n 6 --fast             # 一次性灌音频，压吞吐
python concurrent_test.py --n 6 --url ws://192.168.8.111:8765/v1/realtime
```

输出每路的连接耗时、首包延迟、总耗时、音频时长与 ASR 结果，末尾给汇总统计。

单路逐阶段时间线用 `latency_probe.py`（能看到 STT / LLM / TTS 各自耗时）：

```bash
python latency_probe.py --wav say.wav
```

# 延迟为什么高，以及怎么压到能打电话

## 一句话结论

**原来的瓶颈不是模型能力，是三处工程配置错误。** 修完之后，从「说完话」到「听见回复」由 **15.4 秒降到 1.18 秒**，快了 13 倍。

---

## 一、原来的 15.4 秒花在哪（实测拆解）

用时间线探针（`latency_probe.py`）单路干净环境下跑一遍，逐阶段计时：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 音频推送 | 3.90s | 客户端按真人语速推送，正常 |
| VAD 判定 + 分段 | ~0.4s | 正常 |
| **STT 语音识别** | **6.52s** | ← 问题 1 |
| LLM 生成 | 0.18s | 极快，完全不是瓶颈 |
| **TTS 合成到首块音频** | **8.92s** | ← 问题 2、3 |
| **合计：说完 → 出声** | **15.44s** | |

### 问题 1：STT 用了 CPU 上的 whisper-small，还开了自动语种检测

- `faster-whisper small` + `int8` 在 CPU 上 **RTF = 0.87**，也就是 3.5 秒语音要算 3 秒，几乎实时速度。
- 更糟的是入口脚本写的是 `--faster_whisper_stt_gen_language auto`：每句话都要先跑一遍语种检测，实测 **5.19s vs 固定中文 3.03s**。
- 而且这次它把中文误判成了 **日文（p=0.71）**，识别结果变成 `しろに`。

### 问题 2：TTS 语种误判触发模型重载

上一条的连锁反应。日志原文：

```
TTS - Language change detected: b -> z, voice: zf_xiaobei -> zf_xiaobei
```

Kokoro 的 `_process_kokoro` 在语种变化时会**重新构造整个 `KPipeline`**（要重新加载中文 G2P 那一套）。从 LLM 出文本到 TTS 真正开始，中间 **空转了 8.66 秒**。

### 问题 3：重采样器把音频「挤」出来

这个是隐藏最深的一个。改用 OpenAI 兼容 TTS 之后，首包降到 1.9s，但音频**每秒才吐一块**，1 秒的语音拖了 48 秒才放完。

原因在 `_StreamingFIRResampler`：9880 的 melo TTS 输出 44.1kHz，流水线内部是 16kHz，比例 44100:16000 化简后是 **441:160**，于是它生成了一个 **8821 抽头** 的 FIR 滤波器，每个音频块都做一次超长卷积 —— 在 ARM CPU 上直接爆炸。

## 二、改了什么

### 1. STT / TTS 换成这台机器上现成的快引擎

这台机器上本来就跑着一个 `voice-service`（9880 端口，SenseVoice ASR + melo TTS），是中文优化过的。实测：

| | 原来（容器内本地模型） | 现在（复用 9880） | 提升 |
|---|---|---|---|
| STT | whisper-small CPU `auto` **5.19s** | SenseVoice **0.16s** | **32×** |
| TTS | Kokoro-82M CPU **3.72s** | melo **0.42s** | **9×** |
| 中文准确度 | `希望你以後能夠做得比我還好喲` | `希望你以后能够做的比我还好哟。` | 简体更准 |

因为 9880 的接口协议和 OpenAI 不一样，中间加了一层 `voice_adapter.py` 做协议转换
（`/v1/audio/transcriptions` ↔ `/asr/recognize`，`/v1/audio/speech` ↔ `/tts/vits`）。

顺带好处：9880 不回报 language 字段，Kokoro 那套语种切换重载的问题**从根上消失**。

### 2. 重采样挪到适配层，一次性做完

适配层拿到 44.1kHz 的 WAV 后，用 `soxr` **一次性**重采样到 16kHz，以裸 PCM 返回；
流水线侧声明 `sample_rate=16000`，此时 `up == down`，重采样退化成直通，零开销。

### 3. 内存占用顺带暴跌

因为不再需要每个 pipeline 各加载一套 whisper + kokoro：

| | 原来（6 路空闲） | 现在（6 路空闲） |
|---|---|---|
| 容器内存 | ~9.0 GB | **517 MB** |

## 三、修完之后的实测

### 单路（干净环境）

```
4.26s  音频推送完毕
4.39s  ASR 出文本          (+0.13s)  ← STT
4.87s  首块回复文本        (+0.61s)  ← LLM
5.44s  ★ 首块音频到达      (+1.18s)  ← TTS
5.53s  response.done       (+1.27s)  ← 回合结束，可立刻再说话
音频 1.34s，分 11 块，块间隔中位 11ms，全部 0.44s 内吐完
```

**首包 1.18 秒，回合 1.27 秒结束。**

### 6 路并发（同时全部开口）

| | 旧架构 | 新架构 |
|---|---|---|
| 成功率 | 6/6 | 6/6 |
| 首包中位 | **63s** | **8.1s** |
| 空闲内存 | 12 GB | 517 MB |

并发时首包升到 8 秒，是因为 6 路的 STT/TTS 都要过同一个 9880 服务、LLM 也要过同一个 llama-server，上游排队。实际通话中每路是各说各话，不会同时爆发。

## 四、这样能打电话了吗

**延迟这一关过了。** 通话体验的经验阈值：

| 首包延迟 | 体验 |
|---|---|
| < 800ms | 接近真人，可打断 |
| **1 – 1.5s** | **可以顺畅对话**（当前水平） |
| 2 – 3s | 能忍，但会觉得对方「迟钝」 |
| > 5s | 没法对话 |

剩下要补的是**电话网络接入**，这是另一件事，跟延迟无关：

1. **需要一条 SIP/PSTN 通道**
   - 自建：在这台机器或另一台机器上跑 Asterisk / FreeSWITCH，再配一个 SIP 中继（运营商线路或云通信服务商）
   - 用云：腾讯云 / 阿里云的语音通话服务，拿到 SIP 地址和号码

2. **需要一个音频桥**
   - 电话侧是 RTP 流（通常 8kHz 窄带 G.711），服务侧是 16kHz PCM 的 WebSocket
   - 桥的职责：RTP ↔ PCM 转码、8k↔16k 重采样、按 20ms 帧双向转发
   - 这个流水线已经原生支持打断（barge-in）、VAD 自动断句，桥只要老实转发双向音频就行

3. **需要注意的工程点**
   - 电话是 8kHz 窄带，识别率会低于现在的 16kHz 测试音频，建议先拿真实电话录音回归一遍
   - 根分区只剩 278MB，装 Asterisk 要装到 `/opt` 分区
   - `voice-service`(9880) 和 `llama-server`(8080) 现在是强依赖，电话场景要保证它们常驻

**想继续的话，我可以直接把 Asterisk + 音频桥搭起来**，你只要提供一条 SIP 中继（或者告诉我用哪家云通信）。
